# Retarget resets every target-side step, script or manual; collect and preflight are kept

## Context
A code review found that `RelocationRunner::retarget()` deleted the transfer/restore/verify runs but not the `RelocationCheck` rows a user creates by ticking a script step as skipped ("nothing to transfer"). The skipped state survived a change of destination and the wizard jumped to verify on a server that had received nothing. The question was which check rows a retarget may remove.

## Options considered
- Reset transfer, restore and verify checks, keep collect and preflight (chosen): matches the run deletion list and the modal text "source-side work (preflight, collect) is kept".
- Reset only transfer and restore: verify cannot be ticked as skipped today, but leaving it out lets the two lists drift again.
- Reset every check including collect: simplest, but throws away source-side work the user already did and contradicts the modal.

## Decision
Retarget resets every target-side step, script or manual; collect and preflight are kept

## Consequences
Any step that acts on the target server must be in retarget's reset list, whether it is a script step (runs and check rows) or a manual step (check rows and `<step>:*` sub-check rows). A new target-side step added to `RelocationStep` must be added there too. Source-side steps (preflight, collect) are never reset by retarget.
