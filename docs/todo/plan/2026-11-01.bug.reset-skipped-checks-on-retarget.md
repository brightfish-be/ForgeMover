# Reset skipped transfer/restore checks on retarget

## Request
Retarget keeps skipped transfer/restore as done. app/Services/RelocationRunner.php:104 deletes the runs but not the transfer/restore check rows created by "mark as done". After "Change destination" the wizard shows both as skipped on the new target and jumps to verify.

## Analysis
Bug. Script steps can be "skipped" by ticking the checkbox on the collect/transfer/restore card: `RelocationWizard::confirmScriptSteps()` calls `RelocationRunner::setCheck()`, which creates a `RelocationCheck` row keyed `transfer` / `restore` / `collect`. `Relocation::stepDone()` treats such a row on a script step as done. `RelocationRunner::retarget()` deletes the `transfer`, `restore` and `verify` runs and the check rows of the manual target-side steps (`forge_site`, `deploy_test`, `cutover`), but never the check rows of the script steps, so a skipped transfer/restore survives the move to a new target and `currentStep()` jumps past them. Collect is source-side and its check must stay. No wizard change is needed: the retarget action redirects to the view page, so `mount()` rebuilds `$skipSteps` from the (now deleted) check rows.

## Impacted files
- `app/Services/RelocationRunner.php` — `retarget()` must also delete the check rows of the target-side script steps; the step list is hard-coded strings and should use the enum.
- `tests/Feature/RelocationTest.php` — add a retarget test covering kept vs reset checks and runs.

## Plan
See PRP below.

## Acceptance criteria
- After `retarget()`, `stepDone()` is false for transfer, restore and verify even when they were ticked as skipped before.
- After `retarget()`, a skipped `collect` check and the `preflight` check (and its sub-checks) are still done.
- The `forge_site`, `deploy_test`, `cutover` resets and the run deletions behave as before.
- A Pest test proves the above; `php artisan test` and `vendor/bin/pint --test` pass.

## PRP

### Goal
`RelocationRunner::retarget()` resets every target-side step, script or manual: after a retarget the wizard's current step is never past `transfer` unless the source-side steps alone justify it. Skipped (hand-ticked) transfer, restore and verify checks are removed together with their runs; collect and preflight progress is kept.

### Why
- The "Change destination" modal promises "target-side progress is reset"; today a skipped transfer/restore stays green on a server that has received nothing, and the wizard jumps to verify.
- The fix keeps `retarget()` the single owner of the reset rules (CLAUDE.md: `RelocationRunner` owns the rules).

### Decisions taken
- Which script-step check rows are reset? → transfer, restore and verify (all target-side script steps, mirroring the run deletion on the next line); collect is kept because it only touches the source (default, from the existing run-deletion list and the modal text). (recorded: decisions/2026-11-01.retarget-resets-every-target-side-step.md)
- Keep the hard-coded `['transfer', 'restore', 'verify']` strings? → Derive both the run deletion and the check deletion from one list of `RelocationStep` cases, so the two cannot drift (default, matches the enum-driven style of the rest of the class). (recorded: decisions/2026-11-01.retarget-derives-its-run-and-check.md)
- Refresh the wizard's `$skipSteps` after retarget? → Not needed: the action redirects and `mount()` rebuilds it from `checkDone()` (verified in `RelocationWizard.php:76-103`).

### Known gotchas & guardrails
- Mirror the existing patterns named under Context; do not introduce new ones for this item
- PRESERVE: the early return when a relocation for the same source/site/new target already exists, the "pick a different server" and "still running" guards, and the `temp_domain` / `finished_at` reset.
- PRESERVE: `preflight` and `collect` check rows (and `preflight:*` sub-checks) must survive a retarget.
- The existing manual-step delete uses `orWhere` with an explicit `relocation_id` re-scope; keep that shape (or group with `where(fn)`), never issue a delete that is not scoped to the relocation.
- `Relocation::checkDone()` reads the loaded `checks` relation; in the test call `->refresh()->load('checks', 'runs')` before asserting, as the gating test at the bottom of `RelocationTest.php` does.
- Tests run on in-memory SQLite with the sync queue; `start()` writes a log file under `storage/app/relocations/`, so delete the log directory at the end of a test that creates runs (see the first test in the file).
- Do not touch `undoStep()` / `$skipSteps` handling; that is todo item "Clear skip checkbox on undo and guard running step".

### Approach
In `retarget()`, build one list of target-side steps (`ForgeSite`, `DeployTest`, `Cutover`, `Transfer`, `Restore`, `Verify`) and run the existing step-row + sub-check-row delete loop over all of them; derive the run deletion's `whereIn` from the script members of that same list via `->value`. Add one Pest test in `tests/Feature/RelocationTest.php` that ticks `preflight`, `collect`, `transfer` and `restore` via `setCheck()`, creates a third server, calls `retarget()`, reloads with `load('checks', 'runs')` and asserts `stepDone()` per step and `currentStep() === RelocationStep::ForgeSite`.
